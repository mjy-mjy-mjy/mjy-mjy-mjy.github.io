给这个博客写第三篇文章的时候，出现了一个有点尴尬的场面。

文章本身写得还算顺利，但在开始之前，需要重新交代的东西几乎和上一次一模一样：文章放在哪个目录、文件名怎么命名、Front Matter 有哪几个必填字段、图片要放进以文章为单位的独立目录、正文尽量用第三人称、不要写“随着人工智能技术的不断发展”这类开头、提交前要跑一次构建检查。

这些内容第一次说是必要的沟通，第二次说还能接受，第三次说就变成了纯粹的损耗。模型每次都能理解，但每次也都是从零开始理解。上一轮协作中形成的判断，没有留在任何地方。

## 重复的不是任务，是交代任务的过程

评估 AI 协作效率时，注意力通常集中在模型写得对不对、返工了几次。但把几次协作放在一起看，被重复消耗的其实是另一部分：把任务背景、项目约定和验收标准重新说清楚的那段过程。

这部分成本有几个不太容易被注意到的特点。

它是稳定的。写第一篇文章需要交代的目录结构，写第十篇时还是同一套，并不会因为熟练而减少。

它是隐性的。每次多花的可能只是三五分钟，不会出现在任何统计里，但它决定了一件事值不值得随手交给 AI 去做。需要先铺垫十分钟才能开始的任务，很多时候就自己动手了。

它还是不可靠的。凭记忆复述的规范，每次都会略有出入。这次强调了图片的 alt 文本，下次可能忘了；这次说清楚了不要直接提交主分支，下次可能只说了“提交一下”。规范一旦只存在于对话里，就会随着对话一起消失，而且消失得没有痕迹——没人知道这次少说了哪一条。

> 值得沉淀的，往往不是那个最难的任务，而是那些每次都得重新说一遍的前提。

## Skill 不是更长的 Prompt，而是被固定下来的判断

一个常见的理解是：Skill 就是一段写得比较完整、比较专业的 Prompt。从形式上看确实如此，两者都是文字；但从作用上看，差别在于它们回答的问题不同。

Prompt 回答的是“这一次要做什么”。它天然是一次性的，也应该是一次性的——这次要写的主题、这次的字数、这次希望强调的角度，都不该被固定下来。

Skill 回答的是“这类任务通常应该怎么做”。它描述的是跨越多次任务仍然成立的部分：项目的目录约定、可接受的写作风格、什么情况下需要配图、什么算作真正完成。

区别在于时间尺度。把只属于这一次的要求写进 Skill，下一次就要花力气把它绕开；把每次都要重复的前提留在 Prompt 里，就会永远重复下去。

这也解释了为什么“第三次”是一个合适的触发点。第一次做，还看不出哪些是通用的；第二次做，能感觉到重复，但样本不足以判断规律；到第三次，稳定的部分基本已经暴露出来了，此时抽象出来的规则通常不会跑偏。太早沉淀，固定下来的很可能只是巧合。

## 哪些内容值得沉淀，哪些只是这一次的要求

真正动手写的时候，最容易出问题的一步是分类。同样是上一轮协作里说过的话，去向应该完全不同。

判断标准可以很简单：如果下一次任务的场景完全不同，这条规则还成立吗？成立的写进去，不成立的留在原地。

中间还有一类更麻烦的内容——踩过的坑。“不要把生成式插图里的中文当成准确信息”显然值得保留，但它是不是一条规范，取决于它出现过几次。只出现一次的教训，先记在复盘里，等它第二次出现再提升为规则。

## 分层：让说明、规范和校验各自归位

把所有内容塞进一个文件是可行的，但很快会遇到两个问题：文件越写越长，每次都要整篇读；规范和校验混在一起，改动时不知道会影响什么。

这个博客的发布流程最后落成了这样一个结构：

```text
skills/mujian-blog-publisher/
├── SKILL.md                     入口：什么时候调用，分几种模式
├── references/
│   ├── blog-profile.md          博客定位、目录约定、文件命名
│   ├── writing-style.md         叙述视角、结构偏好、要避免的套话
│   ├── visual-style.md          什么时候配图，用 SVG 还是位图
│   ├── publishing-rules.md      分支、提交、PR 与合并规则
│   └── lessons-learned.md       每次任务的复盘
├── templates/
│   ├── post.md                  文章骨架
│   ├── pull-request.md          PR 正文结构
│   └── preview-shell.html       可离线打开的预览外壳
└── scripts/
    ├── validate-post.mjs        校验文章本身
    └── validate-assets.mjs      校验文章引用的资源
```

这四层的差别，本质上是对模型理解的依赖程度在递减。入口说明完全依赖模型读懂并选择；规范依赖模型在写作时遵守；模板把一部分结构直接固定成文本；到了脚本这一层，模型理解得对不对已经不重要了，结果由执行决定。

分层还有一个实际好处：改动范围可控。调整写作风格只动一个文件，不会波及发布规则；新增一条校验只动脚本，不需要重写规范。如果全部挤在一个文件里，每次修改都要重读全文才敢下手。

## 把“帮我写篇文章”拆成几种模式

规范写清楚之后，还剩一个容易被忽略的问题：同样一句“帮我写篇文章”，可能意味着完全不同的动作范围。

有时候只是想听几个选题；有时候是想要一份初稿；有时候是初稿已经定了，只想看看排版效果；有时候才是真的要提交到仓库。如果不区分，最省事的做法就是每次都执行到底——结果是一句随口的请求引出了一个 Pull Request。

所以入口文件里明确拆了几种模式，每种模式写清楚做到哪一步、不做什么：

- **选题模式**：读现有文章找缺口，给出候选题，不创建任何文件；
- **初稿模式**：产出完整 Markdown，不建分支，不碰 GitHub；
- **预览模式**：生成可以双击打开的单文件 HTML，不修改仓库；
- **发布模式**：建分支、写文件、跑校验、创建 PR，但不合并。

这里最重要的其实不是模式的划分方式，而是每种模式都写明了**边界在哪**。“不做什么”比“做什么”更需要写下来——模型倾向于把事情做完整，如果没有明确的停止点，它会自己补上后面的步骤。

同样的道理适用于安全边界：不直接提交默认分支、不在没有明确要求时合并 PR、不删除旧文章。这些约束平时看不出价值，只在某一次模型判断失误时才会发挥作用。

## 校验脚本决定了一个 Skill 的下限

规范写得再细致，也只是一种期望。真正把期望变成保证的，是那些能跑起来的检查。

这个发布流程里有两个脚本。一个检查文章本身：必填的 Front Matter 字段是否齐全、日期格式是否正确、文件名日期和正文日期是否一致、permalink 有没有和已有文章重复、模板里的占位符是不是还没替换、正文是不是短得不正常。另一个解析正文里的图片引用：文件是否真的存在于仓库中、扩展名和内容是否匹配、每张图有没有 alt 文本、图片有没有被放到别的文章目录下。

它们拦下来的错误大致长这样：

```text
ERROR: Filename date (2026-08-18) does not match front matter date (2026-08-17).
ERROR: Duplicate permalink found in 2026-07-24-prompt-skill-and-mcp.md: /posts/prompt-skill-and-mcp/
Validation failed with 2 error(s).
```

```text
ERROR: Missing asset: /assets/images/posts/skill-layers.svg -> src/assets/images/posts/skill-layers.svg
Asset validation failed with 1 error(s).
```

这些错误有一个共同点：它们都不难，都是“人一分神就会漏掉，但机器永远不会漏”的事情。图片路径少写一层目录，本地预览时可能因为缓存看不出来，部署之后才发现是一张裂图；permalink 复制上一篇忘了改，两篇文章会悄悄抢同一个地址。

完整的验证是三条命令，覆盖范围逐级放大：

```bash
node skills/mujian-blog-publisher/scripts/validate-post.mjs src/posts/示例文章.md
node skills/mujian-blog-publisher/scripts/validate-assets.mjs src/posts/示例文章.md
npm test
```

前两条负责单篇文章，最后一条负责整站——构建产物、内部链接、搜索索引、文章目录是否仍然正确。三条都通过，才是一个可以汇报的结果。

这一点值得强调，是因为 AI 协作里最常见的失败模式并不是写错，而是提前宣布完成。文件生成了、内容看起来合理，就当作任务结束。校验脚本的价值就在于把“看起来完成”和“确实通过”分开：在它给出结论之前，任何完成的说法都还只是猜测。

> 规范定义了目标，脚本才划出了下限。没有下限的规范，靠的仍然是每一次的自觉。

## 规则是从失败里长出来的，不是从设想里

Skill 真正开始产生复利，是在它开始记录失败之后。

第一版规范通常只包含那些一眼就能想到的约定——目录在哪、字段有哪些。而实际执行中暴露的问题往往更具体，也更不容易提前想到：把多张图拼成一张大图当素材，结果任何一处要改都得整张重做；依赖生成式插图里的中文，出现了错字且无法修正；在 Pull Request 已经被合并之后，仍然按“它还开着”继续操作。

这些经验如果只留在当时的对话里，下一个会话完全不知道。写进文件之后，它们才会在下一次任务开始时被读到。

比较实用的做法是把复盘和规范分开存放。复盘保留背景、有效做法和需要避免的做法，允许带有具体情境，甚至可以写得比较啰嗦；只有反复出现、确认可迁移的结论，才提升为规范。这样既不会让规范被一次性的教训污染，也不会让教训彻底丢失。

复盘还有一个容易被忽视的作用：它记录的是“为什么会有这条规则”。半年后回头看一条奇怪的约定，如果找不到它的来历，就只能在“照做”和“删掉”之间猜。

## 什么时候不该写 Skill

反过来说，并不是所有重复都值得沉淀。

任务本身还没稳定的时候不该写。规范会把当前的做法固定下来，如果做法本身还在调整，固定得越早，后面要绕开的东西越多。这时候更适合把做法记在复盘里，等它稳定了再提升。

只会用一两次的事情不该写。维护一份规范是有成本的，它需要随项目变化而更新，过时的规范比没有规范更容易误导——因为它看起来是权威的。

规则之间开始互相矛盾的时候，也不该继续加。一个 Skill 写到某个程度，新增条款会和旧条款冲突：这里说“图能少则少”，那里又要求“每篇至少一张头图”。这种时候需要的不是补充，而是删减和重写。规范的价值来自它被信任，一旦执行者需要自己判断该听哪一条，它就已经开始失效了。

判断标准仍然可以回到那个问题：这件事还会发生多少次，以及每次重新交代要花多少力气。两个答案都不大的时候，直接写一段 Prompt 就够了。

判断的重点从来不是“这个任务复杂不复杂”，而是“这套前提要不要说第三遍”。第一次是沟通，第二次是提醒，第三次就该考虑把它固定下来——固定成模型每次都会读到的规范，以及机器每次都会执行的检查。
