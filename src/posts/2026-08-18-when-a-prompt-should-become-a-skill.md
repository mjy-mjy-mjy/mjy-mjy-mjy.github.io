给这个博客写第三篇文章的时候，出现了一个有点尴尬的场面。

文章本身写得还算顺利，但在开始之前，需要重新交代的东西几乎和上一次一模一样：文章放在哪个目录、文件名怎么命名、Front Matter 有哪几个必填字段、图片要放进以文章为单位的独立目录、正文尽量用第三人称、不要写“随着人工智能技术的不断发展”这类开头、提交前要跑一次构建检查。

这些内容第一次说是必要的沟通，第二次说还能接受，第三次说就变成了纯粹的损耗。模型每次都能理解，但每次也都是从零开始理解。上一轮协作中形成的判断，没有留在任何地方。

## 重复的不是任务，是交代任务的过程

很多人评估 AI 协作效率时，会盯着模型写得对不对、返工了几次。但把几次协作放在一起看，被重复消耗的其实是另一部分：把任务背景、项目约定和验收标准重新说清楚的那段过程。

这部分成本有几个不太容易被注意到的特点。

它是稳定的。写第一篇文章需要交代的目录结构，写第十篇时还是同一套，并不会因为熟练而减少。

它是隐性的。每次多花的可能只是三五分钟，不会出现在任何统计里，但它决定了一件事值不值得随手交给 AI 去做。

它还是不可靠的。凭记忆复述的规范，每次都会略有出入。这次强调了图片的 alt 文本，下次可能忘了；这次说清楚了不要直接提交主分支，下次可能只说了“提交一下”。规范一旦只存在于对话里，就会随着对话一起消失。

> 值得沉淀的，往往不是那个最难的任务，而是那些每次都得重新说一遍的前提。

## Skill 不是更长的 Prompt，而是被固定下来的判断

一个常见的理解是：Skill 就是一段写得比较完整、比较专业的 Prompt。从形式上看确实如此，两者都是文字；但从作用上看，差别在于它们回答的问题不同。

Prompt 回答的是“这一次要做什么”。它天然是一次性的，也应该是一次性的——这次要写的主题、这次的字数、这次希望强调的角度，都不该被固定下来。

Skill 回答的是“这类任务通常应该怎么做”。它描述的是跨越多次任务仍然成立的部分：项目的目录约定、可接受的写作风格、什么情况下需要配图、什么算作真正完成。

区别在于时间尺度。把只属于这一次的要求写进 Skill，下一次就要花力气把它绕开；把每次都要重复的前提留在 Prompt 里，就会永远重复下去。

这也解释了为什么“第三次”是一个合适的触发点。第一次做，还看不出哪些是通用的；第二次做，能感觉到重复，但样本不足以判断规律；到第三次，稳定的部分基本已经暴露出来了，此时抽象出来的规则通常不会跑偏。

## 哪些内容值得沉淀，哪些只是这一次的要求

真正动手写的时候，最容易出问题的一步是分类。

以这个博客的发布流程为例。“文章目录是 `src/posts/`，图片按文章建独立目录”属于项目事实，几乎不会变，应该写进去。“正文以第三人称为主，第一人称只在真实经历处少量使用”属于长期偏好，也应该写进去。“不要把生成式插图里的中文当成准确信息”属于踩过的坑，同样值得保留。

但“这篇文章用一个浏览器端 ToDo 工具当例子”不属于这一类。它是那一篇文章的选择，写进 Skill 就会变成对后续所有文章的束缚。同样，“这次希望结尾克制一点”也只是一次反馈，除非它反复出现，否则不该升格为规范。

判断标准可以很简单：如果下一次任务的场景完全不同，这条规则还成立吗？成立的写进去，不成立的留在对话里。

## 分层：让说明、规范和校验各自归位

把所有内容塞进一个文件是可行的，但很快会遇到两个问题：文件越写越长，每次都要整篇读；规范和校验混在一起，改动时不知道会影响什么。

比较稳定的做法是分层，让每一层承担不同性质的内容。

最上层是入口说明，回答“什么时候该用它”，以及这次要执行到哪一步。选题、写初稿、只做预览、正式提交，需要的动作范围差别很大，把模式拆开可以避免一句“帮我写篇文章”直接引出一个 Pull Request。

中间是长期规范。写作风格、视觉标准、发布与分支规则各自成篇，改其中一份不会牵动其他部分。

再往下是模板。文章骨架、Pull Request 正文结构、预览页外壳，这些东西每次都一样，没有必要重新设计。

最下面是校验脚本。它不解释任何判断，只给出通过或不通过。

这四层的差别，本质上是对模型理解的依赖程度在递减。入口说明完全依赖模型读懂并选择；规范依赖模型在写作时遵守；模板把一部分结构直接固定成文本；到了脚本这一层，模型理解得对不对已经不重要了，结果由执行决定。

## 校验脚本决定了一个 Skill 的下限

规范写得再细致，也只是一种期望。真正把期望变成保证的，是那些能跑起来的检查。

这个博客的发布流程里有两个脚本，一个检查文章本身，一个检查文章引用的资源。它们做的事情并不复杂：确认必填的 Front Matter 字段都在、日期格式正确、文件名日期和正文日期一致、permalink 没有和已有文章重复、模板里的占位符已经全部替换掉；另一个则解析正文里的图片引用，确认文件真的存在于仓库中、扩展名和内容匹配、每张图都有 alt 文本、图片没有放到别的文章目录下。

这些检查有一个共同点：它们都是那种“人一分神就会漏掉，但机器永远不会漏”的事情。

```bash
node skills/mujian-blog-publisher/scripts/validate-post.mjs src/posts/示例文章.md
node skills/mujian-blog-publisher/scripts/validate-assets.mjs src/posts/示例文章.md
npm test
```

前两条负责单篇文章，最后一条负责整站——构建产物、内部链接、搜索索引、文章目录是否仍然正确。三条命令都通过，才是一个可以汇报的结果。

这一点值得强调，是因为 AI 协作里最常见的失败模式并不是写错，而是提前宣布完成。文件生成了、内容看起来合理，就当作任务结束。校验脚本的价值就在于把“看起来完成”和“确实通过”分开：在它给出结论之前，任何完成的说法都还只是猜测。

> 规范定义了目标，脚本才划出了下限。没有下限的规范，靠的仍然是每一次的自觉。

## 复盘要写进文件，而不是留在对话里

Skill 真正开始产生复利，是在它开始记录失败之后。

第一版规范通常只包含那些一眼就能想到的约定，而实际执行中暴露的问题往往更具体：一次把多张图拼成大图当素材，结果无法单独修改；一次依赖生成式插图里的中文，出现了错字；一次在 Pull Request 已经被合并之后，仍然按“它还开着”继续操作。

这些经验如果只留在当时的对话里，下一个会话就完全不知道。写进文件之后，它们才会在下一次任务开始时被读到。

比较实用的做法是把复盘和规范分开存放。复盘保留背景、有效做法和需要避免的做法，允许带有具体情境；只有反复出现、确认可迁移的结论，才提升为规范。这样既不会让规范被一次性的教训污染，也不会让教训彻底丢失。

## 什么时候不该写 Skill

反过来说，并不是所有重复都值得沉淀。

任务本身还没稳定的时候不该写。规范会把当前的做法固定下来，如果做法本身还在调整，固定得越早，后面要绕开的东西越多。

只有自己会用一两次的事情不该写。维护一份规范是有成本的，它需要随项目变化而更新，过时的规范比没有规范更容易误导。

判断标准仍然可以回到那个问题：这件事还会发生多少次，以及每次重新交代要花多少力气。两个答案都不大的时候，直接写一段 Prompt 就够了。

判断的重点从来不是“这个任务复杂不复杂”，而是“这套前提要不要说第三遍”。第一次是沟通，第二次是提醒，第三次就该考虑把它固定下来——固定成模型每次都会读到的规范，以及机器每次都会执行的检查。
