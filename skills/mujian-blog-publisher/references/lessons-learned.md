# 生产复盘与经验

本文件记录可复用经验，不记录只属于单篇文章的临时内容。新经验应包含背景、有效做法和需要避免的做法。

## 2026-07-24：Prompt、Skill 和 MCP 文章

### 背景

文章最初以概念解释为主，随后经历了叙述视角调整、示例替换、Mermaid 适配、视觉方案重构和 GitHub PR 交付。

### 有效做法

- 用“开发浏览器端 ToDo 小工具”贯穿全文，比用“让 AI 写博客”作为示例更自然，也更能解释工具调用和工程流程；
- 以第三人称讲解为主，在真实经验处少量使用第一人称，文章更像个人技术博客；
- 先制作独立 HTML 预览，再写入仓库，可以让用户在提交前确认正文、配图和卡片布局；
- 氛围插图适合放在文章开头，但图片中的精确信息应尽量少；
- 带中文和复杂关系的信息图使用 SVG，文字、布局和可访问性更可控；
- Workflow 和问题诊断采用 HTML/CSS 卡片，比多张 Mermaid 连续出现更适合阅读；
- 图片按文章建立独立目录，方便以后修改、删除或迁移；
- CI 必须等待明确的成功结果后再汇报验证通过。

### 需要避免

- 不要默认认为“技术文章就应该用 Mermaid”；Mermaid 解决结构表达，不一定解决视觉质量；
- 不要把头图、信息图和工具图拼成一张大图作为正式素材；
- 不要依赖生成式图片中的中文文字，容易出现错字和不可控排版；
- 不要在未确认项目真实配置文件名时创建替代配置文件；
- 不要在用户或其他流程已经合并 PR 后继续假设 PR 仍然打开；
- 不要用空文件、临时占位文件或无意义提交解决 Git 分支问题；
- 不要把“预览效果接近”表述为“线上一定完全一致”；正式页面仍受博客布局和主题影响。

### 已形成的长期规则

- 第三人称为主，少量第一人称增加真实性；
- 抽象概念使用真实项目或小工具贯穿；
- 默认每篇文章只安排少量高价值视觉内容；
- 复杂中文信息图优先 SVG；
- 预览确认与仓库提交分为两个阶段；
- 不直接提交默认分支，不自动合并 PR；
- 每次发布都进行文章、资源和构建三类验证。

## 追加复盘的格式

```markdown
## YYYY-MM-DD：文章或任务名称

### 背景

### 有效做法

### 需要避免

### 已形成的长期规则
```

只有能够在以后任务中复用的结论，才能进入“长期规则”。
