# 视觉与配图规范

## 总体原则

图片必须承担信息或阅读节奏上的作用。默认不是“每个章节都配图”，而是整篇文章选择 1～3 个真正值得视觉化的位置。

## 推荐组合

一篇中长技术文章通常采用：

- 1 张文章头图或氛围插图；
- 1～2 张精确信息图；
- 若流程文字较多，使用 HTML/CSS 步骤卡片或时间线；
- 若需要表达简单关系，可按需使用 Mermaid。

## 选择格式

### SVG

适合：

- 概念关系；
- 系统结构；
- 工具连接；
- 带中文标签的信息图；
- 需要长期维护和清晰缩放的图。

要求：

- 中文文字由 SVG 文本节点精确控制；
- 提供 `title`、`desc` 或准确的 `alt`；
- 浅色背景下清楚，深色模式下通过容器或独立版本保持可读；
- 不使用小于正文可读范围的密集文字。

### WebP / PNG

适合：

- 氛围插图；
- 产品界面截图；
- 复杂纹理和照片。

要求：

- 生成式插图中尽量不放中文；
- 头图优先采用横向比例；
- 控制文件体积；
- 不把生成式界面当作真实产品截图。

### Mermaid

适合：

- 简单流程；
- 状态转换；
- 开发者更关心结构而非视觉精致度的图。

不适合：

- 文章需要编辑插画感时；
- 四张以上连续流程图；
- 节点中文很多且需要精细排版时；
- 用图只是为了打断文字时。

## HTML/CSS 组件

优先用于：

- 步骤列表；
- 问题诊断卡片；
- 对比项；
- 可在移动端自动变成单列的内容。

公共样式应使用语义明确、冲突概率低的类名，例如：

- `.post-figure`
- `.article-steps`
- `.article-step`
- `.diagnosis-grid`
- `.diagnosis-card`

新增公共 CSS 前先搜索是否已有相同能力，避免重复样式文件。

## 图片目录

每篇文章独立存放：

```text
src/assets/images/posts/<article-slug>/
├── hero.webp
├── concept-map.svg
└── tool-workbench.svg
```

文件名使用小写英文和连字符，不使用日期、空格或无意义编号。

## Markdown 引用

推荐使用带说明文字的 HTML：

```html
<figure class="post-figure">
  <img
    src="/assets/images/posts/article-slug/concept-map.svg"
    alt="准确描述图中信息"
    loading="lazy"
  >
  <figcaption>说明这张图希望读者看到什么。</figcaption>
</figure>
```

首屏头图可不启用懒加载，正文信息图默认 `loading="lazy"`。

## 独立预览

预览页应：

- 能够双击直接在浏览器打开；
- 尽量使用单文件 HTML，或提供 ZIP 包；
- 展示桌面端主要排版；
- 至少具备基本移动端响应式布局；
- 明确标注“未上传博客”；
- 不承诺与正式博客像素级一致；
- 正式提交前再次在真实博客布局中检查。

## 可访问性

- 每张信息图必须有准确 `alt`；
- 装饰性图片使用空 `alt`；
- 图中颜色不能是唯一的信息区分方式；
- 正文中的关键信息不能只存在于图片；
- 图片说明不重复 alt，而是补充图的阅读重点。
